# Agent Note: 公共词库按汉字精确查询

Status: implemented

## Problem

`lookup_dictionary` 的默认候选查询把汉字原样发给只接受输入编码的 `candidates` 接口，产生 400。即使先转拼音，有限候选没有出现某个词也不能证明未收录。

## Decision

提供只读 `/v1/input/listed`，针对 1～7 个基本汉字的词语，先使用发布词库注音，再用现有 `listed_pinyin_batch` 精确检查该编码和词语是否收录，返回 `word`、`code`、`listed`。注音能为未收录词语逐字推导读音，因此注音成功本身不当成收录证据。任何引擎错误或异常响应都明确失败。

公共工具支持显式 `listed`；默认 `candidates` 收到纯汉字且方案为默认或拼音时自动转为精确查询。纯汉字且 `scheme=shuangpin` 时自动转入 `annotate`，保留显式 `profile`，由固定版本的 Rust Engine 生成完整双拼按键码、两键分段与原全拼。显式 `annotate` 支持相同参数；四种方案为小鹤、自然码、首道和微软，未知方案或五笔反查明确失败。普通编码候选保持原语义。三个工具入口共用请求构造，不单独给 QQ 写一套转换。

汉字按键码反查只扩展注音的显式双拼请求；默认全拼响应保持原样。Go 不保存第二份键位表，也不让模型根据拼音猜码。双拼编码成功仍不证明词语收录。

## History audit

检索云端现有笔记，公共工具决定见 [公共查询工具](../../implemented/feature/2026-10-16-qqbot-public-tools.md)。该决定仍适用；本篇补充汉字与编码的输入边界和收录判断依据，不接入个人词库。

## Alternatives considered

- 提示模型先注音再查候选：只改说明即可减少 400，但模型仍可能直接传汉字，且候选截断无法给出可靠的未收录结论。工具入口自动选择精确查询，结果使用底层查重能力。
- 放宽候选接口接收汉字：调用方最省事，但候选接口原本以编码和输入方案为契约，汉字精确查询的返回形状也不同。新增独立操作保留原契约。

## Testing

- 已复现默认汉字查询返回 400，修复后的回归确认它进入精确查询；普通拼音查询不改变。
- 单测覆盖已收录、未收录、注音失败、查重失败和畸形响应，不能把故障当成未收录。
- 固定提交 `592e3db682c9a5f0094d081aca5d6647d21c235b`（上游 PR metasequoiaime/msime#8265）的真实引擎与发布词库已通过 HTTP 和 QQ 工具入口验证。

- 双拼回归通过真实引擎和发布词库，覆盖四种方案、显式注音、误送汉字的候选查询及其他操作默认参数；HTTP 对非法方案和非汉字保持拒绝。

- 引擎升级沿用上游已经明确的日文 `nn` 规则；既有罗马字 HTTP 冒烟改用无歧义的 `kon'nichiha`，仍断言返回 `こんにちは`，避免绑定旧版 `nn` 的消费规则。

- 生产同款模型通过实际本地 HTTP 服务执行四种方案反查，四次完整码均匹配合成词预期；真正 MCP stdio 握手后再对四种方案逐一调用，均成功。该验证不经过真实 QQ 群。

## Consequences

一次精确查询需要两次只读引擎调用，共享调用方超时；返回收录状态仅指发布拼音词库，不代表五笔或个人词库。当前引擎仅对七字以内词语反查完整词组读音，更长词语采用逐字读音，可能误判多音字；精确检查因此拒绝超过七字的输入，避免错误的未收录结论。
