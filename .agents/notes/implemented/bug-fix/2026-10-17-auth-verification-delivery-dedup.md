# Agent Note: 验证码有效期内复用邮件

Status: implemented

## Problem

同一邮箱或手机号在验证码仍有效时再次请求，会重新占用全站发信额度并再次投递相同用途的邮件。Lark SMTP 的免费额度按日计算，重复点击和网络重试会很快耗尽额度；原服务还把全站上限写成 500，高于当前 450 封的免费上限。

## Decision

验证码挑战继续每次生成新的 `challenge_id`，但在同一目标已有未过期的本版本验证码时复用同一个随机种子，从服务端密钥和目标重新计算相同的六位验证码，不再次调用邮件或短信供应商。每个新挑战仍保存自己的 `code_hash`，所以旧挑战和新挑战都只能各消费一次，挑战仍在五分钟后失效。旧版本没有种子的活动挑战不复用，避免无法重建原验证码。

活动挑战查询使用 PostgreSQL 部分索引，状态跨副本共享；目标的分钟、小时和每日限流仍然生效，只有实际首次投递才计入 `delivery-global`。`delivery-global` 统一限制为 450 封/日，验证码和下载链接共用该额度。

## Alternatives considered

- 把明文验证码或原始挑战 ID 存入数据库：可以直接复用，但扩大数据库泄露后的离线猜码能力，破坏现有只存摘要的边界。
- 只把目标限流窗口延长到五分钟：能减少发送，但会让用户在邮件丢失时只能等待，且不能处理请求重试带来的重复投递。
- 在进程内缓存验证码：单副本可行，但生产是多副本部署，缓存会失效并重新发信；跨请求状态必须放进 PostgreSQL。

## Testing

- PostgreSQL 集成测试验证首次请求只发送一次，限流窗口过后新挑战复用原验证码且不增加全站发信计数，复用挑战可以完成登录。
- OpenAPI 生成器和用户认证文档同步记录 `reused` 响应字段。

## Consequences

同一目标在有效期内的重试不会收到新邮件；用户若确实没有收到第一封邮件，需要等待挑战过期后重新请求。验证码种子不是响应字段，也不能单独用于登录。新增索引会在启动迁移时补齐，旧数据库需要完成一次正常迁移。
