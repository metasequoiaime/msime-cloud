# Agent Note: 抑制 SMTP 永久拒收地址

Status: implemented

## Problem

部分收件地址会被 SMTP 在 `RCPT` 阶段明确拒收，或在邮件被 `DATA` 接受后异步退信。服务当前只返回通用发送失败，不记住已确认无效的地址；同一地址再次请求会继续尝试投递并占用 Lark 的每日额度，还会让发件箱持续收到退信警告。

## Decision

服务在 `RCPT` 阶段收到 5xx 永久拒收时，把 `provider` 和目标的哈希写入 PostgreSQL 抑制表，默认抑制 30 天。后续验证码和下载链接请求在预留全站发信额度前直接返回 `delivery_failed`，不会再次连接 SMTP。永久拒收的本次额度预留会退回；临时 4xx、认证失败或 `DATA` 阶段错误不推断地址永久无效，也不写入抑制表。

抑制表只保存哈希和有限原因，不保存收件地址；过期记录由既有每小时清理任务删除。由于普通 SMTP 提交接口不能同步观察 `DATA` 之后的退信，异步退信仍需要供应商的反馈接口或人工处理，不能由本改动伪造成功判断。

## Alternatives considered

- 对所有发送错误都加入地址黑名单：实现简单，但会把临时网络、认证和供应商故障误判为地址失效，导致合法用户被长期锁死。
- 只在应用进程内保存失败地址：单副本有效，但多副本部署会重复尝试，且重启后丢失抑制状态。
- 仅做域名 MX 查询：只能判断域名是否存在，无法识别具体邮箱，不能阻止收件服务器在 `RCPT` 或异步投递阶段拒收。

## Testing

- 单元测试验证 550 永久拒收会被分类，451 临时错误不会被分类。
- PostgreSQL 集成测试验证永久拒收不会重复发送，并退回全站发信额度。
- 完整 Go 测试通过。

## Consequences

已确认永久无效的地址不再反复消耗发信额度，退信数量和无效 SMTP 连接都会下降。30 天抑制期内用户若修复了邮箱，只能等待期限到期；异步退信仍未自动导入，因此需要后续接入 Lark 的退信反馈才能覆盖这类失败。
