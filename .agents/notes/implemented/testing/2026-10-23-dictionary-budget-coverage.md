# Agent Note: 词库性能预算区分覆盖率插桩

Status: implemented

## Problem

验证 QQ 管理员 MCP 时，完整 PostgreSQL 覆盖率检查被未改动的 `TestDictionaryRowsCommentQueryBudget` 阻断。50 ms 和 500 ms 采样在覆盖率构建下均失败，普通 race 构建连续三次通过。生产函数被覆盖率插桩，位于测试文件的旧参考实现不被插桩，直接比较两者耗时会把插桩开销当成产品退化。

## Decision

所有构建仍执行两份实现的基准测量，并要求当前实现比旧实现分配更少内存。原有 1.2 倍速度门槛只在没有覆盖率插桩时检查；CI 的普通 race 全仓检查继续约束速度，数据库覆盖率检查继续运行负载与分配验证，不修改生产函数。

## Alternatives considered

- 覆盖率模式跳过整个测试最省时间，但会失去这组长注释输入的分配回归，因此保留实际测量和分配断言。
- 放宽速度阈值改动最小，但无法给插桩开销提供跨机器、跨编译器的合理上界，也会弱化普通构建的速度约束。
- 在覆盖率测试中另启无插桩 Go 构建能获得可比耗时，但会嵌套构建并重复 CI 已有的普通 race 测试，增加依赖与资源开销。

## Testing

修正后，普通 race 构建以 1 秒采样连续通过三次，覆盖率构建以 500 ms 采样连续通过三次，原普通构建速度门槛保持不变。完整数据库测试的覆盖率合并后为 account 92.50%、server 94.60%，通过原有门禁。首次整包中该测试失败，其他 server 测试通过；修正后只复测受影响的性能测试，没有重跑整包数据库测试。

## Consequences

覆盖率任务单独运行时不再据耗时判断速度，需保留 CI 的普通 race 检查。覆盖率统计本身、生产查询与分配约束不变。
