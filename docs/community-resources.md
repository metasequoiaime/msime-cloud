# Community resource API

`/v1/community/resources` exposes data-only `dictionary`, `reply` and `phrase` works separately from existing skin APIs. `GET` requires `kind`; `q` searches names, `offset` paginates 20 works, and `scope=saved|mine` requires a user session. Detail includes content, revision, saves, ownership and rating state. User IDs and credentials are never published.

List and detail accept `fields=moderation`: the caller's own works then carry `moderation` (`approved`, `pending` or `removed`); other users' works and anonymous requests never do, and the removal reason is never returned. Without the parameter the response is byte-for-byte unchanged, because released clients reject unknown fields. Any other `fields` value is 400 `invalid_fields`. Works are public as soon as they are published (post-moderation), so clients only need to badge `removed` works as 已下架.

Authenticated `POST` accepts a stable UUID, kind, name (1–32 characters), description (0–280), content and revision. New works use revision 0; updates use the current revision. Identical retries return the existing version; differing stale updates return 409. Only the owner may update or delete; an account may publish at most 50 resources. Names, descriptions, words and prompts are screened: a block-level sensitive word returns 422 `blocked_content` and nothing is saved; when the word list cannot be loaded the request returns 503 `screening_unavailable` with `Retry-After`, and the client should retry later. Account deletion cascades through resources, saves and ratings.

Dictionary content contains 1–128 explicit `{kind,code,word,weight}` entries. Kinds are pinyin, wubi (Wubi 86), wubi98 (Wubi 98), english and quick. The fixed Engine validates and normalizes each entry; normalized duplicates are rejected. No personal dictionary or learning history is read implicitly. Reply content contains a prompt of 1–2000 characters; dictionaries cannot carry prompts and replies cannot carry entries. Unknown fields are rejected. No code, remote assets or provider credentials are part of either format.

Phrase packs (kind `phrase`) carry `content.phrases`: 1–200 `{text,group}` items, each text 1–2000 UTF-16 code units, where line breaks are allowed but no other control characters; `group` is optional and at most 32 characters. Phrase packs cannot carry `entries` or `prompt`. Clients install them locally into the code-less phrase store and then call the existing download counter. `POST /{id}/apply` answers 400 `unsupported_kind` for phrase packs, because there is nothing to merge on the server. Reports use kind `phrases`. List, detail, download, save and rating accept `kind=phrase` exactly as they do for the other kinds.

`PUT /{id}/save` accepts `{saved:bool}` and is idempotent. `PUT /{id}/rating` accepts 1–5 stars from any signed-in user; saving first is no longer required. Rating one's own work is still 403 `save_before_rating_or_own_resource` (the code keeps its old name and now only means "your own work"), and a missing or removed work is 404 `resource_not_found`. Reading a saved work returns its latest revision. Clients explicitly preview and apply updates; the server never overwrites a subscriber's personal words.

Deploy the additive `internal/account/community_schema.sql` migration before the new image. Adding `phrase` replaces the `community_resources.kind` and `community_reports.kind` CHECK constraints: on startup `Ready` probes both and, when they are the old ones, replaces them under the migration advisory lock (looked up by name in `pg_constraint`, so repeated starts are no-ops). With least-privilege runtime roles run `-migrate-users` with a DDL-capable role first; older images keep working against the new constraints because they never write `phrase`. Production tables belong to the existing owner role; grant runtime DML on the three new `community_resource*` tables, not schema CREATE. Older images ignore the added tables and can roll back without removing them.

`python3 scripts/community_resources_seed.py` renders a transaction for the original starter works: three prompts, two word packs and four official phrase packs (邮件签名、日期与时间、客服常用语、会议纪要模板). Review before execution. UUIDs are deterministic, repeated execution does not replace content or fabricate saves/ratings. Native validation is covered by `TestStarterResourcesUseValidContent` with `MSIME_ENGINE_TEST_BINARY` set.
